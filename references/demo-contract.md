# HTML Demo 的交付标准

目标是能拿着操作并讨论的业务场景。不要交付只有标题、说明和假按钮的展示页，也不要把问题清单直接变成产品界面。

## 形态

- 默认一个 `demo.html`，内嵌样式和脚本，无CDN、远程字体、外部图片、API密钥或服务端依赖，可用 `file://` 直接打开。若用户已有项目结构或明确要求其他技术，沿用并给出准确运行办法。
- 按当前业务组织布局、信息层次与文案。桌面和窄屏可读，表单有label，操作可用键盘，错误说明清楚。
- 核心操作要改变可见状态：例如录入→校验→结果→修正/重试，或选择任务→操作→状态更新。每个主要可点击控件都实现作用，或明确禁用及理由。
- 实现当前场景有关的空状态、错误/缺输入、返回和重置。不要为无关场景机械补大量页面。
- AI建议用确定的模拟响应即可，但在使用处标“模拟AI”；不能显示“已发送给客户”或“已真实审批”这类虚假执行结果。示例记录标明模拟，数据不写入外部系统。

## 对齐区域

独立页签或可折叠区，至少包含：本轮要解决的问题、角色、范围/非目标、主要R-ID与场景映射、假设、当前未决定的D-ID、演示步骤、反馈输入和下载。展示版本及“待需求方对齐”；真实反馈确认后只能对已确认范围改状态。

用 `textContent` 或等价转义插入用户输入和反馈，避免把输入当HTML执行。下载文件使用UTF-8，中文、换行和特殊字符要保留；不悄悄上传。重置Demo不应无提示清除需求方尚未导出的反馈。

## 检查

1. 逐项核对R-ID与可操作场景；找出被添加但无来源的功能，删除或显式标为待定假设。
2. 在可用浏览器运行主流程、相关空/错状态、返回/重置和反馈下载，检查下载内容、控制台异常、意外远程请求、中文输入，以及桌面/约390px窄屏。检查实际视觉效果，不只读源码。
3. 反馈输入中文与 `< > &` 等字符，确认呈现为文本并能完整导出。刷新后数据若不保留，说明必须先导出；不称其为团队共享评审系统。
4. 把实际结果写入review.md；未能运行的检查写“未验证”并列手工步骤，不用静态语法通过代替浏览器验证。
5. M08只能支持已测试范围的交付；M02/M03/M09所需的真实使用、访谈、付费和效果仍需实际发生。把这些待验证项留给对齐与后续试用。
